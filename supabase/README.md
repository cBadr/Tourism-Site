# إعداد Supabase — دليل خطوة بخطوة

هذا الدليل مكتوب لمن لم يستخدم Supabase من قبل. اتبع الخطوات بالترتيب ولا تتخطَّ أي خطوة.

---

## ١) إنشاء مشروع Supabase

1. ادخل إلى <https://supabase.com> وسجّل الدخول (يمكن التسجيل بحساب GitHub أو Google).
2. اضغط **New project**.
3. اختر اسماً للمشروع (مثلاً `tours-platform`)، واختر كلمة مرور قوية لقاعدة البيانات **واحفظها في مكان آمن** (لن تحتاجها يومياً، لكنها مطلوبة عند الاسترجاع).
4. اختر المنطقة الأقرب لعملائك: **Frankfurt (eu-central-1)** خيار جيد لمصر.
5. اضغط **Create new project** وانتظر دقيقة أو دقيقتين حتى يجهز المشروع.

## ٢) تنفيذ ملفّي الهجرة (Migrations) بالترتيب

1. من القائمة الجانبية في لوحة Supabase افتح **SQL Editor**.
2. اضغط **New query**.
3. افتح الملف `supabase/migrations/0001_core.sql` من المشروع على جهازك، وانسخ **كامل محتواه** والصقه في المحرر.
4. اضغط **Run** (أو Ctrl+Enter). يجب أن ترى رسالة نجاح مثل `Success. No rows returned`.
5. كرّر نفس الخطوات مع الملف الثاني `supabase/migrations/0002_seed_settings.sql`.
   - **الترتيب مهم:** الملف `0001` ينشئ الجداول، والملف `0002` يملؤها بالقيم الافتراضية.
6. للتأكد: افتح **Table Editor** من القائمة الجانبية — يجب أن ترى جدولين: `site_settings` (فيه ٥ صفوف) و `profiles` (فارغ حالياً).

## ٣) نسخ المفاتيح إلى `.env.local`

1. في لوحة Supabase افتح **Project Settings** (أيقونة الترس) ثم **API**.
2. في مجلد المشروع على جهازك، انسخ الملف `.env.example` إلى ملف جديد باسم `.env.local` (نفس المجلد الرئيسي للمشروع).
3. املأ القيم:
   - `NEXT_PUBLIC_SUPABASE_URL` ← القيمة الموجودة تحت **Project URL**.
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` ← المفتاح المسمّى **anon / public** (وقد يظهر باسم publishable key في اللوحات الأحدث).
   - `SUPABASE_SERVICE_ROLE_KEY` ← المفتاح المسمّى **service_role**. **تحذير:** هذا المفتاح يتجاوز كل الحماية — لا تضعه في أي مكان عام ولا ترسله لأحد.
4. احفظ الملف ثم أعد تشغيل خادم التطوير (`pnpm dev`) حتى يقرأ القيم الجديدة.

## ٤) ترقية حسابك إلى admin

1. سجّل حساباً جديداً من الموقع نفسه (أو أنشئ مستخدماً من **Authentication ← Users ← Add user** في لوحة Supabase).
2. عند إنشاء أي مستخدم يُنشأ له صف تلقائياً في جدول `profiles` بدور `customer`.
3. افتح **SQL Editor** ونفّذ الأمر التالي بعد استبدال البريد ببريدك:

```sql
update public.profiles
set role = 'admin'
where id = (select id from auth.users where email = 'YOUR_EMAIL@example.com');
```

4. للتأكد نفّذ:

```sql
select u.email, p.role from public.profiles p join auth.users u on u.id = p.id;
```

يجب أن يظهر بريدك بدور `admin`.

> ملاحظة أمان: لا يستطيع أي مستخدم تغيير دوره بنفسه من التطبيق — الترقية تتم فقط من SQL Editor (كما فعلت الآن) أو بواسطة admin موجود مسبقاً.

## قائمة التحقق — خطآن شائعان وكيف تكتشفهما

### ١. صلاحيات anon تأتي من مصدرين — وكلاهما مطلوب

الوصول لأي جدول يمر بطبقتين منفصلتين:

- **GRANT** على مستوى الجدول (صلاحية SQL كلاسيكية)، و
- **سياسة RLS** تسمح بالصفوف.

إن نقصت واحدة منهما تعطّل الوصول، لكن الأعراض تختلف:

| العرض | السبب | العلاج |
|---|---|---|
| خطأ `permission denied for table ...` | الـ GRANT ناقص | نفّذ `grant select on public.site_settings to anon, authenticated;` |
| لا خطأ لكن النتيجة **مصفوفة فارغة** رغم وجود بيانات | سياسة RLS ناقصة أو شرطها لا ينطبق | راجع السياسات في **Authentication ← Policies** وتأكد من تنفيذ `0001_core.sql` كاملاً |

الملف `0001_core.sql` يضبط الطبقتين معاً — إن عبثت بالسياسات يدوياً من اللوحة، تذكّر أن اللوحة قد تضيف سياسة دون grant أو العكس.

### ٢. UPDATE أو DELETE «ينجح» لكن صفر صفوف

تحت RLS، إذا لم ينطبق شرط `using` على أي صف، فإن `update`/`delete` **لا يرجع خطأ** — يرجع نجاحاً مع صفر صفوف متأثرة. هذا أخطر فخ في Supabase لأنك تظن أن العملية تمت وهي لم تمس شيئاً.

كيف تكتشفه:

- في **SQL Editor**: راقب الرسالة — `Success. No rows returned` بعد UPDATE قد تعني «لم يُعدَّل شيء». أضف `returning *;` في نهاية الأمر لترى الصفوف المعدّلة فعلاً؛ إن رجعت فارغة فالسياسة منعتك بصمت.
- في كود التطبيق: أضف `.select()` بعد `.update()`/`.delete()` وافحص طول النتيجة:

```ts
const { data } = await supabase
  .from("site_settings")
  .update({ value: newValue })
  .eq("key", "brand")
  .select(); // إن رجعت data فارغة فالتعديل لم يحدث — غالباً لست admin
```

السبب المعتاد هنا: المستخدم الحالي ليس `admin` في جدول `profiles`، فتمنعه سياسة الكتابة بصمت. راجع الخطوة ٤ أعلاه.
