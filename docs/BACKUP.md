# النسخ الاحتياطي والاستعادة — ماذا تفعل لو ضاعت القاعدة الآن

> هذا الملف مكتوب ليُقرأ **في يوم سيّئ**: القاعدة ذهبت، والموقع لا يعمل، وأنت
> تريد خطوات لا شروحاً. لذلك القسم ٣ أولاً، وكل ما قبله وبعده مرجع.
>
> ما في القاعدة اليوم ليس بيانات تجريبية يمكن إعادة توليدها: إعداداتك ومحتوى
> موقعك ومتعهدوك وأسعارهم وحجوزاتك و**دفترك المالي** (`ledger_entries` سجل
> append-only لا يُعاد بناؤه من شيء آخر).

---

## ١. الخلاصة في دقيقة

| الأمر | ماذا يفعل |
|---|---|
| `pnpm db:backup` | ينسخ القاعدة كلها إلى ملف مضغوط بطابع زمني في `backups/` |
| `pnpm db:restore -- --list` | يعرض النسخ المتاحة |
| `pnpm db:restore -- <ملف> --dry-run` | يفحص الملف ويعرض ما سيحدث — **بلا أي كتابة** |
| `pnpm db:restore -- <ملف>` | الاستعادة الفعلية — تسأل تأكيداً مكتوباً قبل أي كتابة |

**افعل الآن، قبل قراءة الباقي:**

```bash
pnpm db:backup
```

وانسخ الملف الناتج إلى مكان **ثانٍ** (قرص خارجي أو مجلد سحابي مزامَن). نسخة
واحدة على القرص نفسه ليست نسخة احتياطية — هي نفس القرص مرتين.

## ٢. `pnpm db:backup` — ماذا ينتج بالضبط

```
▶  نسخ احتياطي — الخادم PostgreSQL 17.6
   الوجهة   : postgres.xxxx@aws-1-eu-west-1.pooler.supabase.com:5432/postgres
   المخططات : public · auth · storage
   الملف    : ...\backups\tours-01_2026-08-13_16-08-24.dump

✅ اكتملت النسخة الاحتياطية
   الحجم   : 1.36 ميغابايت
   المدة   : 41.1 ثانية
   الجداول : 69 — auth: 23 · public: 38 · storage: 8
   محتوى الأرشيف: 1196 مدخلاً، منها 69 جدولاً ببياناته ✔ فُحص
```

| نقطة | التفصيل |
|---|---|
| الصيغة | أرشيف `pg_dump` بصيغة **custom** (مضغوط داخلياً بـ gzip). يُستعاد بـ `pnpm db:restore`، ويُحوَّل إلى SQL نصّي عند الحاجة بـ `pg_restore -f out.sql <file>` |
| الوجهة | `backups/` — **محجوب في `.gitignore`**؛ الملف يحوي بيانات عملاء وحسابات دخول، ورفعه إلى git تسريبٌ لا يُتراجَع عنه بحذف الملف لاحقاً |
| المخططات | `public` (المنتج كله) · `auth` (حسابات الدخول) · `storage` (الدلاء والسياسات) |
| ما يُستثنى عمداً | `vault` (أسرار Supabase) و`realtime` و`graphql` — تديرها المنصة وتُبنى في أي مشروع جديد، ونسخها يوقع أخطاء ملكية بلا فائدة |
| «✔ فُحص» | بعد كتابة الملف يُقرأ فهرسه بـ `pg_restore --list`. **نسخة لم تُقرأ ليست نسخة**؛ لو تعذّرت قراءتها يفشل الأمر ولا يترك ملفاً يوحي بالسلامة |
| سجل تراكمي | `backups/index.log` — سطر لكل نسخة (التاريخ، الحجم، عدد الجداول، المدة) |

### المتطلبات

1. **`DATABASE_URL`** في `.env.local` بصيغة **Session pooler** لا المضيف المباشر
   (المباشر IPv6 فقط ⇒ `ENOTFOUND`). التفاصيل في `handover/ENVIRONMENT.md` القسم ٤.
2. **`pg_dump`** على الجهاز — يأتي ضمن حزمة عميل PostgreSQL. السكربت **لا يفترض
   وجوده**: يفحص أولاً، وإن غاب طبع تعليمات التثبيت ولم يرمِ خطأ غامضاً.

```powershell
# ويندوز — الأسرع
winget install -e --id PostgreSQL.PostgreSQL.18
```

المثبّت الرسمي: <https://www.postgresql.org/download/windows/> — يكفي تعليم
**Command Line Tools** في شاشة المكوّنات (لا حاجة لتشغيل خادم Postgres محلياً).
ماك: `brew install libpq && brew link --force libpq` · دبيان:
`sudo apt install postgresql-client-18`.

بعد التثبيت **أغلق الطرفية وافتحها من جديد**. وإن كانت مثبّتة في مكان غير معتاد:

```
PG_DUMP_PATH=C:\Program Files\PostgreSQL\18\bin
```

> ⚠ إصدار `pg_dump` يجب أن يكون **مساوياً أو أحدث** من إصدار الخادم (اليوم
> Postgres 17). الأقدم لا يقرأ مخطط الأحدث — والسكربت يرفض العمل بدل أن ينتج
> ملفاً ناقصاً بصمت.

## ٣. ⛑ ضاعت القاعدة — ماذا تفعل الآن، خطوة بخطوة

### ٣-أ أولاً: شخّص الحالة (دقيقتان، ولا تتخطَّها)

| السؤال | الجواب | اذهب إلى |
|---|---|---|
| هل مشروع Supabase نفسه ما زال موجوداً في اللوحة؟ | **لا** — محذوف أو موقوف | **٣-ج** |
| هل الجداول موجودة والبيانات ناقصة/تالفة (حذف خاطئ، هجرة أفسدت شيئاً)؟ | نعم | **٣-د** |
| هل الجداول نفسها اختفت؟ | نعم | **٣-د** |
| هل المشكلة أن التطبيق لا يتصل فقط؟ | نعم | **لا تستعد شيئاً** — راجع `DATABASE_URL` والمفاتيح في `handover/ENVIRONMENT.md`. الاستعادة على قاعدة سليمة تُتلف ما هو سليم |

> **قبل أي استعادة، إن كانت القاعدة الحالية ما زالت تُقرأ ولو جزئياً:**
> ```bash
> pnpm db:backup
> ```
> نسخة الحالة المعطوبة قد تحوي صفوفاً كتبت بعد آخر نسخة سليمة. الاستعادة تمحوها
> نهائياً، ودقيقة واحدة الآن تشتري لك خيار الرجوع.

### ٣-ب اعرف أي ملف تستعيد

```bash
pnpm db:restore -- --list
pnpm db:restore -- tours-01_2026-08-13_16-08-24.dump --dry-run
```

الـ `--dry-run` يطبع: محتوى الملف (عدد المدخلات والجداول والمخططات)، والوجهة،
و**عدد صفوف أكبر جداول القاعدة الحالية** — أي ما ستفقده بالضبط. لا يكتب شيئاً.

### ٣-ج المسار الأول — مشروع Supabase جديد (الأنظف)

هذا أنظف مسار لأن `public` يبدأ فارغاً فلا تصادم ولا بقايا.

1. **أنشئ مشروع Supabase جديداً** — واختر **نفس الإقليم** إن أمكن
   (`aws-1-eu-west-1`) كي يبقى زمن الاستجابة كما هو.
2. **حدّث `.env.local`**: `NEXT_PUBLIC_SUPABASE_URL` ·
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` · `SUPABASE_SERVICE_ROLE_KEY` (Project
   Settings ← API) و`DATABASE_URL` (زر Connect ← **Session pooler** ← URI).
3. **استعد البنية والبيانات معاً:**
   ```bash
   pnpm db:restore -- tours-01_2026-08-13_16-08-24.dump
   ```
   اكتب `استعادة` (أو `RESTORE`) عند السؤال. الأمر يبني الجداول والدوال
   والسياسات والصلاحيات **ثم** يحمّل البيانات — لا حاجة لـ `pnpm db:migrate` قبله.
4. **حسابات الدخول** — الأرشيف يحوي مخطط `auth`، لكن استعادته إلى مشروع جديد
   ليست تلقائية في هذا السكربت (`--schema=public` هو الافتراضي). أبسط وأأمن مسار:
   ```bash
   node scripts/invite-admin.mjs <بريدك>
   ```
   ثم اضبط كلمة المرور من `/admin/set-password`، وأعد دعوة المتعهدين بـ
   `node scripts/invite-subcontractor.mjs <بريده>`.
   > **مهم:** `public.profiles.id` مرتبط بـ `auth.users(id)`. المستخدم الجديد
   > يأخذ معرّفاً جديداً، فلن يرث صف `profiles` القديم. راجع `/admin` بعد كل
   > دعوة وتأكد من الدور والربط بالمتعهد.
5. **ملفات المخزن** (صور الوسائط وإيصالات الدفع) — القسم ٦.
6. **تحقق:**
   ```bash
   pnpm db:test     # ثماني مجموعات، كلها تطبع ALL PASSED
   pnpm db:migrate  # يقرأ schema_migrations المستعاد ويطبّق ما بعده فقط
   pnpm build
   ```
7. **انسخ فوراً:** `pnpm db:backup` — أول نسخة بعد كارثة هي أهم نسخة.

### ٣-د المسار الثاني — نفس المشروع، البيانات تالفة

```bash
pnpm db:backup                                   # (١) صوّر الحالة المعطوبة
pnpm db:restore -- <ملف> --dry-run               # (٢) اقرأ ما ستفقده
pnpm db:restore -- <ملف>                         # (٣) نفّذ، واكتب: استعادة
pnpm db:test && pnpm build                       # (٤) تحقق
pnpm db:backup                                   # (٥) انسخ من جديد
```

ما يفعله السكربت في الخطوة (٣) بالترتيب:

1. يقرأ فهرس الأرشيف ويرفض الملف التالف قبل أي شيء.
2. يعرض الوجهة ومحتوى القاعدة الحالية، ويطلب تأكيداً **مكتوباً**.
   لا يعمل خارج طرفية تفاعلية، **ولا يوجد وسيط لتخطّي التأكيد** — عملية تمحو
   الدفتر المالي لا يجوز أن تنطلق من جدولة أو سكربت بالخطأ.
3. يلتقط الكائنات التي **خارج** `public` وتعتمد على دواله، ويحفظ تعريفها في
   `backups/dependents-before-restore_<وقت>.sql`، ثم يُسقطها مؤقتاً (القسم ٤-ب).
4. ينفّذ `pg_restore --clean --if-exists --no-owner --single-transaction`
   على مخطط `public` — **معاملة واحدة ذرّية**: أي خطأ يُرجع القاعدة كما كانت.
5. يعيد ما أسقطه في الخطوة ٣ — سواء نجحت الاستعادة أو فشلت.
6. يطبع عدد صفوف الجداول **قبل وبعد**، وقائمة ما يلزم فعله بعدها.

**إن فشلت الاستعادة:** القاعدة لم تتغير (معاملة واحدة). اقرأ رسالة `pg_restore`،
ثم جرّب:

```bash
pnpm db:restore -- <ملف> --allow-errors
```

هذا يتخطّى الأخطاء ويكمل — **وهو غير ذرّي**: قد تنتهي بقاعدة نصف مستعادة. لا
تستعمله إلا بعد فشل الوضع الذرّي، وشغّل `pnpm db:test` بعده مباشرة.
وإن استمر الفشل، فالمسار **٣-ج** (مشروع جديد) أسرع من مطاردة العلة.

### ٣-هـ ولا توجد أي نسخة؟

بالترتيب:

1. **لوحة Supabase ← Database ← Backups** — إن أتاحت خطتك استعادة، فهي أسرع
   وأكمل من أي شيء هنا (تشمل ملفات المخزن والحسابات). القسم ٧.
2. **دعم Supabase** (Support ← New ticket) — حتى بلا نسخ في اللوحة قد يكون لديهم
   ما يساعد، خصوصاً خلال ساعات من الحادث. **أبلغهم فوراً؛ النافذة تضيق بالوقت.**
3. **إعادة البناء من الصفر**: `pnpm db:migrate` يعيد **البنية** كاملة من ملفات
   `supabase/migrations/*.sql` (٢٥ ملفاً في المستودع). البنية تعود؛ **البيانات لا
   تعود**. أعد إدخال الإعدادات والمتعهدين والأسعار يدوياً.
   والدفتر المالي التاريخي… لا يعود. لهذا يوجد هذا الملف.

## ٤. قرارات مثبَّتة — لا تنقضها

### ٤-أ لماذا تُستعاد **البنية والبيانات معاً**، ولماذا `--data-only` ممنوع

ترتيب أرشيف `pg_dump` يضع **البيانات قبل المشغّلات والقيود والسياسات**. فُحص
على الأرشيف الفعلي: أول جملة `COPY` عند السطر 9096، وأول `CREATE TRIGGER` عند
23775، وأول `CREATE POLICY` عند 24341. أي أن الاستعادة الكاملة تحمّل الصفوف
**ولا مشغّل واحد يعمل**.

أما `--data-only` فيحمّل الصفوف في قاعدة مشغّلاتها **قائمة**. وفي هذا المشروع
تُكتب قيود الدفتر بمشغّلات داخل معاملة الحدث نفسه (`handover/CONVENTIONS.md`
القسم ٢). فاستعادة بيانات فقط تعني: كل صف حجز يُعيد إطلاق مشغّله ⇒ قيد دفتر
جديد فوق القيد المستعاد ⇒ **خزينة مضاعفة**. الخطأ صامت والأرقام تبدو معقولة.

> **لا تضف `--data-only` إلى `scripts/db-restore.mjs`.**

### ٤-ب لماذا يُسقط السكربت تسعة كائنات مؤقتاً

`pg_restore --clean` يُصدر `DROP FUNCTION` بلا `cascade`، وهو يعرف كيف يُسقط
سياسات `public` قبل دوالها — لكنه **لا يعرف شيئاً عمّا هو خارج `public`**. وفي
هذه القاعدة يوجد بالضبط:

| الكائن | يعتمد على |
|---|---|
| ٨ سياسات على `storage.objects` (`media_*` و`receipts_*`) | `public.is_admin()` · `public.receipt_upload_allowed()` |
| مشغّل `on_auth_user_created` على `auth.users` | `public.handle_new_user()` |

بدون معالجة، أول `DROP FUNCTION "public"."is_admin"()` يفشل بـ
`cannot drop function is_admin() because other objects depend on it` — ومع
`--single-transaction` تُلغى الاستعادة كلها. (فُحص فعلياً على القاعدة الحية داخل
معاملة مُلغاة.)

فالسكربت يلتقط تعريفها من الكتالوج **مؤهَّلاً بالكامل** (بـ `search_path = ''`)،
ويحفظه في ملف إنقاذ، ويُسقطها، ثم يعيدها بعد الاستعادة نجحت أو فشلت.

**نافذة السقوط ثوانٍ، وأثرها إغلاق لا انفتاح:** RLS تبقى مفعّلة على
`storage.objects` بلا سياسات ⇒ الرفع والقراءة **ممنوعان**، ولا يُكشف شيء.

**إن فشلت الإعادة** (يطبعها السكربت بصوت عالٍ): شغّل محتوى
`backups/dependents-before-restore_<وقت>.sql` كما هو في SQL Editor بلوحة
Supabase. وحتى ذلك الحين: الصور لا تظهر ورفع الإيصالات لا يعمل، وأي حساب جديد
يُنشأ بلا صف `profiles` فلا يدخل `/admin` ولا `/portal`.

### ٤-ج الصلاحيات تُستعاد، الملكية لا

`--no-owner` يُسنِد الملكية إلى الدور المتصل (`postgres`) لأن أدوار Supabase
الداخلية ليست ملكنا. أما **الصلاحيات** (`grant`/`revoke`) فتُستعاد كما هي —
٣٢٤ `GRANT` و١١٦ `REVOKE` في هذا الأرشيف. سطور `revoke` حمّالة: Supabase تمنح
`anon` صلاحيات واسعة افتراضياً على الجداول الجديدة، منها `TRUNCATE` **وهي لا
تخضع لـ RLS إطلاقاً**. حذف الصلاحيات من الاستعادة يفتح الجداول.

## ٥. الوجهة الثانية والوجهة البعيدة

نسخة واحدة على القرص نفسه ليست نسخة احتياطية. رتّبها حسب الجهد:

### أسهلها اليوم — بلا اعتمادات ولا إعداد

المشروع نفسه يعيش داخل `C:\Users\Badr\OneDrive\...`، فمجلد `backups/` **يُزامَن
إلى OneDrive تلقائياً**. هذا يعطيك نسخة سحابية مجاناً — بشرطين:

- تأكد أن المجلد ليس "Free up space" فقط؛ افتح `backups` في المستكشف وتحقق أن
  الأيقونة تقول إن الملف مرفوع فعلاً.
- OneDrive **مزامنة لا أرشفة**: حذف الملف محلياً يحذفه من السحابة (وإن كان
  يبقى في سلة المحذوفات ٣٠ يوماً). فهي طبقة أولى لا وحيدة.

### وجهة ثانية بمسار — قرص خارجي أو مجلد Google Drive أو مشاركة شبكة

في `.env.local`:

```
BACKUP_COPY_TO=D:\tours-backups
```

بعد كل نسخة ناجحة يُنسخ الملف إلى هناك. يقبل أي مسار: قرص USB، مجلد
Google Drive/Dropbox المزامَن، أو `\\server\share`. **بلا أي اعتماد.**

### وجهة برفع خارجي — FTP أو غيره

```
BACKUP_UPLOAD_CMD=rclone copy "{file}" myremote:tours-backups
```

`{file}` يُستبدل بمسار الملف. أمثلة أخرى:

| الوجهة | الأمر |
|---|---|
| FTP/SFTP بـ rclone | `rclone copy "{file}" ftpremote:/backups` |
| WinSCP (FTP/SFTP) | `winscp.com /command "open ftp://user:pass@host" "put {file} /backups/" "exit"` |
| curl إلى FTP | `curl -T "{file}" ftp://host/backups/ --user اسم:كلمة` |

> ⚠ **ما لم يُبنَ عمداً:** لا يوجد تكامل مضمَّن مع FTP أو Google Drive أو غيره.
> لم تُحدَّد وجهة ولا اعتمادات، وبناء رفع لوجهة لا اعتماد لها يعني اختراع
> افتراضات تُكتشف يوم الحاجة. الخطّاف أعلاه يقبل **أي** أداة تختارها.
> وحين تختار وجهة: مكان اعتماداتها محجوز في `.env.example` تحت
> «الوجهة البعيدة — ينتظر اختيار بدر».

### الاحتفاظ

بلا ضبط: **لا يُحذف أي ملف أبداً**. لتقليم القديم:

```
BACKUP_KEEP=14      # أبقِ الأحدث ١٤ واحذف ما قبلها
```

### رموز الخروج

| الرمز | المعنى |
|---|---|
| `0` | نجح كل شيء |
| `1` | فشلت النسخة نفسها — **لا يوجد ملف صالح** |
| `2` | النسخة المحلية سليمة، لكن `BACKUP_COPY_TO` أو `BACKUP_UPLOAD_CMD` فشل |

## ٦. ما **لا** تشمله هذه النسخة

| ما هو | لماذا | ماذا تفعل |
|---|---|---|
| **ملفات مخزن Supabase Storage** — صور الوسائط (`media`) وإيصالات الدفع (`receipts`) | تعيش خارج Postgres. الأرشيف يحفظ صفوف `storage.objects` أي **أسماء** الملفات وبياناتها الوصفية وسياساتها ودلاءها — **لا محتواها** | نزّلها يدوياً من لوحة Supabase ← Storage ← الدلو ← Download، أو بـ [Supabase CLI](https://supabase.com/docs/reference/cli) / rclone. وبعد أي استعادة: `storage.objects` سيشير إلى ملفات قد لا تكون موجودة ⇒ صور مكسورة وإيصالات مفقودة |
| مخطط `vault` | أسرار تديرها المنصة، وغير مستعملة في هذا المشروع (لا تشفير أسرار فيه — القرار في `docs/phase-briefs/PHASE-11.md`) | لا شيء |
| `realtime` · `graphql` | تبنيها Supabase في أي مشروع جديد | لا شيء |
| **متغيرات البيئة** (`.env.local`) | محجوبة في git عمداً، وفيها مفاتيح البوابات والتوكنات | احتفظ بنسخة منها في مدير كلمات مرور. **لا تضعها في `backups/`** ولا في git |
| **إعدادات Vercel والدومين** | خارج القاعدة | (لا نشر بعد — مؤجَّل) |

## ٧. ماذا توفّر Supabase نفسها؟

> **لا تخمين هنا.** بحثتُ في المستودع كله عن أي إشارة إلى خطة مشروع Supabase
> المستعملة — **لا توجد**. لا في `docs/` ولا في `handover/` ولا في الإعدادات.
> فلا أستطيع أن أقول لك ماذا تشمل خطتك.

**كيف تعرف بنفسك (دقيقتان):**

1. لوحة Supabase ← مشروعك ← **Database** ← **Backups**.
   إن رأيت قائمة نسخ يومية بتواريخ ⇒ عندك نسخ مُدارة، واقرأ مدة الاحتفاظ المكتوبة.
   إن رأيت رسالة ترقية ⇒ لا نسخ مُدارة على خطتك الحالية.
2. **Project Settings ← Billing** ⇒ اسم الخطة.
3. التفاصيل الرسمية والمحدَّثة: <https://supabase.com/docs/guides/platform/backups>

**اكتب ما تجده هنا** — هذا الجدول فارغ عمداً حتى تملأه بحقيقة مشروعك:

| البند | ما وجدتَه في لوحتك | التاريخ |
|---|---|---|
| اسم الخطة | ‏ | ‏ |
| نسخ يومية مُدارة؟ | ‏ | ‏ |
| مدة الاحتفاظ | ‏ | ‏ |
| PITR (استعادة إلى لحظة)؟ | ‏ | ‏ |

**وبأي حال — سواء وفّرت خطتك نسخاً أم لا — `pnpm db:backup` يبقى ضرورياً:**

- النسخ المُدارة تعيش في حساب Supabase نفسه. لو ضاع الحساب أو أُغلق المشروع
  (فوترة، خطأ بشري) ضاعت معه.
- استعادة النسخة المُدارة غالباً تعني استعادة المشروع كله لا جدولاً واحداً.
- ملفك المحلي يُفتح ويُقرأ ويُنقل إلى أي مشروع آخر بلا انتظار أحد.

## ٨. الجدولة — مؤجَّلة بوعي

**لا جدولة تلقائية اليوم، والسبب أن الجدولة تحتاج نشراً — وهو مؤجَّل (`D-35`).**
`vercel.json` يعرّف مهامّ مجدولة، لكنها لا تعمل قبل وجود مشروع Vercel، **ولن
تصلح لهذا الغرض أصلاً**: النسخ الاحتياطي يحتاج `pg_dump` (ملف تنفيذي) ووجهة
تخزين دائمة، وكلاهما غير متاح في بيئة دالة بلا حالة.

**حتى ذلك الحين، الجدولة الموصى بها محلية** — Task Scheduler على ويندوز:

```
البرنامج : C:\Program Files\nodejs\node.exe
الوسائط  : scripts\db-backup.mjs
البدء في : C:\Users\Badr\OneDrive\Desktop\Tours-01
```

اضبط `BACKUP_KEEP` كي لا يمتلئ القرص. ولاحظ أن مهمة مجدولة لا يراها أحد حين
تفشل — راجع `backups/index.log` أسبوعياً. (`db-restore.mjs` **لا يعمل** من
جدولة إطلاقاً — يرفض العمل خارج طرفية تفاعلية عمداً.)

**عند النشر (المرحلة ١٣):** المكان الصحيح لهذا هو GitHub Actions أو خادم يملك
قرصاً — لا دالة Vercel.

## ٩. جرّب الاستعادة قبل أن تحتاجها

> **نسخة لم تُجرَّب استعادتها ليست نسخة احتياطية — هي أمنية.**

**⚠ إفصاح صريح:** مسار الاستعادة **المدمِّر** لم يُنفَّذ على هذه القاعدة الحية
(لأن تنفيذه يعني تدمير بياناتك للتجربة). **الذي جُرِّب فعلاً:** إنتاج الأرشيف
وقراءة فهرسه · توليد سكربت الاستعادة كاملاً وفحص ترتيبه · التقاط الكائنات
التسعة التابعة وإسقاطها وإعادتها داخل معاملة مُلغاة · وكل مسارات الرفض
(بلا ملف، ملف غير موجود، مخطط غير موجود، بلا طرفية، `--dry-run`).

**التجربة الحقيقية الآمنة** (نصف ساعة، تشتري ثقة كاملة):

1. أنشئ مشروع Supabase **تجريبياً** مجانياً.
2. انسخ `.env.local` إلى `.env.restore-test` وضع فيه مفاتيح المشروع التجريبي.
3. شغّل الاستعادة عليه:
   ```powershell
   $env:DATABASE_URL = "<رابط المشروع التجريبي>"
   node scripts/db-restore.mjs backups\<آخر ملف>
   ```
   > ⚠ تحقق **مرتين** أن `DATABASE_URL` يشير إلى المشروع التجريبي قبل الضغط.
   > السكربت يطبع الوجهة قبل السؤال — **اقرأها**.
4. `pnpm db:test` على المشروع التجريبي ⇒ ثماني مجموعات `ALL PASSED`.
5. احذف المشروع التجريبي، وسجّل نتيجة التجربة في `docs/ROADMAP.md`.

### إيقاع دوري مقترح

| متى | ماذا |
|---|---|
| قبل كل `pnpm db:migrate` بهجرة جديدة | `pnpm db:backup` |
| قبل أي تغيير كبير من `/admin` (أسعار، تسوية، حذف) | `pnpm db:backup` |
| أسبوعياً | `pnpm db:backup` + تحقق أن الملف وصل الوجهة الثانية |
| شهرياً | تجربة استعادة كاملة (أعلاه) |
| قبل الإطلاق | تجربة استعادة + ملء جدول القسم ٧ |

## ١٠. مرجع سريع

### متغيرات البيئة

| المتغير | إلزامي؟ | الوظيفة |
|---|---|---|
| `DATABASE_URL` | **نعم** | الاتصال بالقاعدة — صيغة Session pooler |
| `PG_DUMP_PATH` | لا | مجلد `bin` لأدوات PostgreSQL إن لم تكن في PATH |
| `BACKUP_DIR` | لا | مجلد النسخ (الافتراضي `backups/`) |
| `BACKUP_SCHEMAS` | لا | المخططات المنسوخة (الافتراضي `public,auth,storage`) |
| `BACKUP_COPY_TO` | لا | مجلد ثانٍ يُنسخ إليه الملف بعد كل نسخة |
| `BACKUP_UPLOAD_CMD` | لا | أمر رفع خارجي، `{file}` = مسار الملف |
| `BACKUP_KEEP` | لا | عدد النسخ المحتفظ بها (بلا ضبط: لا حذف) |

### الأوامر

```bash
pnpm db:backup                              # نسخة كاملة
pnpm db:backup -- --schemas public          # مخططات محددة
pnpm db:backup -- --out D:\backups          # مجلد وجهة لهذه المرة

pnpm db:restore -- --list                   # النسخ المتاحة
pnpm db:restore -- <ملف> --dry-run          # فحص بلا كتابة
pnpm db:restore -- <ملف>                    # استعادة (تأكيد مكتوب إلزامي)
pnpm db:restore -- <ملف> --schema=storage   # مخطط آخر بدل public
pnpm db:restore -- <ملف> --allow-errors     # غير ذرّي — بعد فشل الوضع الذرّي فقط

# تحويل نسخة إلى SQL نصّي قابل للقراءة أو للصق في SQL Editor
pg_restore -f out.sql backups\<ملف>.dump
# استعراض محتوى نسخة بلا فتحها
pg_restore --list backups\<ملف>.dump
```

### الملفات

| الملف | دوره |
|---|---|
| `scripts/db-backup.mjs` | النسخ |
| `scripts/db-restore.mjs` | الاستعادة |
| `scripts/lib/pg-tools.mjs` | إيجاد أدوات PostgreSQL وفحص إصدارها وتحويل `DATABASE_URL` |
| `backups/` | النسخ + `index.log` + ملفات إنقاذ الكائنات التابعة — **محجوب في git** |
| `supabase/migrations/*.sql` | إعادة بناء **البنية** من الصفر (٢٥ ملفاً) — لا البيانات |
